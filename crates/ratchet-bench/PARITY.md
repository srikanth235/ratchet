# ratchet-bench: parity with `packages/bench` and `infra/images/scripts/ratchet-candidate-ctr.c`

`packages/bench` (TypeScript) is the executable spec. This file maps every TS test case to the Rust test that ports it,
lists what was dropped or changed on purpose, and says how behaviour identity is checked. The setuid launcher
(formerly `ratchet-candidate-ctr.c`, deleted) is ported as the `ratchet-candidate-launcher` binary of this crate and is what the images install; its notes are at the end.

## How "behaviour-identical" is verified

| Check | Where | What it proves |
|---|---|---|
| **Golden fixtures** from the TS code | `tests/golden.rs` + `tests/golden/*.json` (generated by `tests/golden/generate.mjs`, which imports `packages/bench/src` through `tsx`) | The generated shell scripts are the security boundary of the remote bench, so they are compared **byte for byte**: `checkoutScript` (133 inputs: isolation x snapshot x container x pinned x prune x launcher + 14 refusals), `stepScript` (122 inputs, kinds x isolation x container x holdout x deps mount + 6 refusals), `depsBuildScript` (16), `imageBuildScript` (13), `imageRestoreFragment` / `ensureImageLoaded` / `ctrFunction` / `containerRun` / `wrapStep` / `sq`. ~70 of them are compared in full text, the rest by sha256. Also: `protectedPcre` (1,500 random + curated glob lists vs the TS regex translation, including V8's `RegExp.source` escaping), `depsKey` / `imageKey` (every key material variation), `parseDepsManifest` / `parseImageManifest` (valid manifests and ~60 mutations: accept/reject and the exact error text), `parseDockerfile`, `parseJsonc`, `normalizeRepoRelative`, `resolveImageSource` + `environmentFilesOf` on 23 trees, strategy environments, guardrail texts, `logKey`, sentinel parsing, `nodeShimScript`. |
| **Reviewable snapshots** | `tests/snapshots.rs` (insta) | Six representative scripts (checkout with user isolation, with snapshot + container, confirm bench step on the host and in the container, setup in the container with the deps mount, the npm snapshot job) as `.snap` files for review. |
| **Property tests** | `tests/properties.rs` | `sq` round-trips any text through bash; `fill` never rescans substituted text; UTF-16 order is a total order; `lockfile_changes` is symmetric/sorted/empty-iff-equal; repo-relative paths never escape; every parser of repository text (Dockerfile, JSONC, launcher config, bench output, globs) never panics; the launcher environment never carries `RATCHET_TRACE` or `AWS_*`. |
| **End-to-end with the real scripts** | `tests/runners.rs`, `remote_deps.rs`, `remote_image.rs` | The generated scripts run under local bash through `testkit::LocalFakeCompute` (the TS `LocalFakeCompute`): `aws s3 cp` is a directory copy, `docker`, `pnpm`, `npm`, `setpriv`, `iptables`, `chown`, `pkill` and the launcher are shims; real `git`, `tar`, `sha256sum`, `grep -P`, `zstd` when installed. |
| **Launcher against the real syscalls** | `tests/launcher.rs` | As root with `setpriv`: the compiled launcher code made setuid root switches uid/gid, drops groups, sets `no_new_privs`, scrubs the environment, refuses a bad configuration. |

The tests pass with and without `zstd` on the host (checked with a PATH that hides it): the snapshot / image builders pick
the compression at run time and the restore follows the manifest.

## Tests that run on Linux only

The bench's remote, dependency-snapshot and image machinery only ever runs on Linux bench hosts; on other platforms the crate
has to compile and its pure-logic tests run. The integration tests that execute the generated host scripts with local bash and
GNU `tar` / `zstd` / `grep -P` / coreutils shims (`tests/remote_deps.rs`, `tests/remote_image.rs`, the `remote` / `remote_specifics` modules of `tests/runners.rs`, `remote_script_helpers` in `tests/units.rs`) and the setuid launcher
(`src/launcher.rs`, `tests/launcher.rs`, its binaries) are `cfg(target_os = "linux")`. CI runs them on ubuntu-latest.

## Dropped or changed on purpose

| What | Why |
|---|---|
| `integration.test.ts` (LocalBenchRunner on `examples/demo-search` with a real `tsc` build) | It tests the TypeScript demo, not the bench: it needs the TS toolchain and 20 s of load generation. The same pipeline is covered by `runners.rs` with a bash bench. An end-to-end run on the demo belongs to the `ratchetd` / `ratchet bench` crates. |
| The vacuous remote variant of "can keep candidate-only protected files when pruning is off (local)" | The TS case returns early for the remote runner. The local case is `local_can_keep_candidate_only_protected_files_when_pruning_is_off`. |
| Fixture bench and check scripts are bash (`bench/bench.sh`, `tests/check.sh`) instead of node (`bench.mjs`, `check.mjs`); the `node -e` probes of the harness and container tests are bash | The Rust crate needs no JavaScript runtime to be tested. The fake `node` of the dependency tests is a shim that prints `v22.22.0` (the TS tests compared with `process.version`). |
| `node-path`: the tests run a bash stand-in for the Electron binary and for node instead of the real node; "the real runtime works in a PATH-less environment" uses an explicit runtime | Same reason. `NodeRuntime::Current` means "the first `node` on PATH, PATH untouched when there is one"; a host that embeds the engine in Electron passes `NodeRuntime::Explicit(NodeRuntimeInfo::electron(..))`. Shim directories are removed by `cleanup_node_shims()` (the TS used `process.once('exit')`; Rust has no exit hook). |
| `LocalBenchRunner` / `RemoteBenchRunner` take `Arc<dyn GitHost>` (the TS took `Pick<GitHost, 'checkout' \| 'resolveRef'>`) | Core's port trait is used as is; the testkit `LocalGitHost` implements all of it. |
| `AbortSignal` is `CancellationToken`; `onProgress` is the `ProgressBenchRunner::run_with_progress` method (`BenchRunner::run` is `run_with_progress` without a callback) | Core's `BenchRunner::run` has no progress parameter. `BenchQueue` takes an `Arc<dyn ProgressBenchRunner>`; `NoProgress` adapts any `BenchRunner`. |
| `BenchError` / `BenchAbortedError` / `BenchCancelledError` are the variants `Infra` / `Aborted` / `Cancelled` of one `BenchError`; `BenchError` converts to `PortError` (`Aborted`, `Cancelled` -> `PortError::Cancelled`) | Idiomatic Rust; `is_abort()` is the TS `name === 'AbortError'`. |
| `LocalBenchRunner` `nodeRuntime: false` is `NodeRuntime::Disabled`; `Partial<StepTimeouts>` is a full `StepTimeouts` (default `DEFAULT_TIMEOUTS`) | No partial structs. |
| `BenchQueue.submit` returns a `BenchTicket` with `wait()` (consuming) and `cancel()`; `subscribe` has no unsubscribe handle; it must run inside a Tokio runtime | `promise` and `cancel` are split because a `Future` cannot be both awaited and cancelled through one handle. |
| `glob` that the JavaScript `RegExp` constructor refused (inverted range `[z-a]`, unmatched `)` after translation) makes `protectedPcre` throw in TS; Rust emits the pattern, and `grep -P` then fails the same way (and the core matcher never matches it) | The regex engines differ; core's port already documents the same difference for `matches_glob`. 2 of the 1,500 random globs. |
| `resolveImageSource` reports a devcontainer parse error with `serde_json`'s message instead of V8's | Only the message tail differs (`... (comments and trailing commas are allowed): <parser message>`); the golden test compares the prefix. |
| `parseDepsManifest` / `parseImageManifest` keep `bytes` as `u64` and `createdAt` as `i64` | The TS kept any finite number; both fields are informational. |
| `parseSentinels`: a JSON array payload is accepted with no fields, as `typeof [] === 'object'` did | Kept for identity; nothing reads fields of such a line. |
| `sq` cannot throw: the script builders reject NUL bytes up front (`reject_nul`) and return `BenchError` | Same refusal, different place. |
| Script templates use `fill()` with `{{name}}` placeholders instead of JS template literals | Readability; every template is pinned by the golden tests. An unknown placeholder panics, so a typo can never reach a script. |
| Sorting of names (`environment` file names, `lockfileChanges`) uses JavaScript's UTF-16 order (`shell::js_cmp`), not byte order | Keys and generated manifests must equal the TS ones for names outside the BMP. |

## The setuid candidate launcher

`src/launcher.rs` (logic) + `src/bin/ratchet-candidate-launcher.rs` (entry point, configuration path compiled in) port
the former `infra/images/scripts/ratchet-candidate-ctr.c`. Same protocol, same exit codes (70 internal, 77 not allowed, 78 refused
argument, 126 / 127 not executable / not found), same messages (`ratchet-candidate: ...`):

1. read `/ratchet/launcher.conf` with `O_NOFOLLOW`; it must be a regular file, owned by root, not group/other writable; one
   read of at most 127 bytes; `<caller uid> <target uid> <target gid>` and nothing else;
2. the REAL uid must be the caller uid; the target must be neither root (uid or gid 0) nor the caller;
3. build the environment while the harness's values are still known: `RATCHET_CANDIDATE_{DIR,HOME,TMP}` are required,
   `PATH` is `RATCHET_CANDIDATE_PATH`, else `PATH`, else the default; the candidate gets PATH, HOME, TMPDIR, USER, LOGNAME,
   LANG and the leading `NAME=value` arguments only; `RATCHET_TRACE` and `AWS_*` as arguments are refused (78);
4. `setgroups([])`, `setresgid`, `setresuid`, verify all four ids, prove root cannot be regained (`setuid(0)` and
   `seteuid(0)` must fail), `PR_SET_NO_NEW_PRIVS`;
5. close every descriptor from 3 up to `min(sysconf(OPEN_MAX), 65536)`, `chdir` to the checkout, `execve` the command.

Differences from the C program, all in the stricter direction:

- a uid or gid in the configuration must fit in 32 bits and carries no sign (`sscanf("%lu")` accepted `-1` and a number
  above 2^32 that was checked as a `unsigned long` but then truncated to `uid_t`);
- `execvp` is emulated: the command is looked up in the PATH the launcher built (as `environ = envp; execvp(..)` did),
  with the `ENOEXEC` -> `/bin/sh` fallback and the `EACCES` memory; a command with a NUL byte is refused;
- the crate forbids `unsafe`: the syscalls go through `nix` (no `libc` calls are made by hand).

Test seam: `tests/launcher.rs` runs the same `launcher::run` through a second binary,
`ratchet-candidate-launcher-seam`, that takes the configuration path from the environment. It only exists with the
`launcher-seam` feature (a dev-dependency feature of this crate's own tests), is never built by `cargo build`, and a setuid
program must not take its configuration path from its caller, which is why the production binary does not.

Build and install (done by CI and the image build, see below):

```text
RUSTFLAGS='-C target-feature=+crt-static' CARGO_PROFILE_RELEASE_STRIP=symbols cargo build --release -p ratchet-bench \
    --bin ratchet-candidate-launcher --target x86_64-unknown-linux-gnu        # or aarch64-unknown-linux-gnu
install -d -m 0700 -o root -g root /usr/local/libexec/ratchet
install -m 4755 -o root -g root target/<triple>/release/ratchet-candidate-launcher \
    /usr/local/libexec/ratchet/ratchet-candidate-ctr
```

The installed name and path (`CANDIDATE_HELPER`) are unchanged, so the generated scripts need no change.

### The image build swap (done)

All three steps of the swap are done:

1. `.github/workflows/images.yml` (job `launcher`) builds the binary with the command above for `x86_64-unknown-linux-gnu`
   (`ubuntu-24.04`) and `aarch64-unknown-linux-gnu` (native `ubuntu-24.04-arm`), installs it with the image script into a
   scratch prefix as a check (digest, 4755 root:root in a 0700 directory, exit 77 without a `launcher.conf`), records the
   SHA-256 and uploads `ratchet-candidate-launcher-x86_64` / `-arm64` (binary + `.sha256`). glibc static-pie, not musl: it is the
   libc the Rust tests run against, and the launcher does no name-service lookups.
2. `infra/images/scripts/35-candidate-launcher.sh` no longer compiles anything and no longer installs gcc: Packer uploads the
   binary (`launcher_binary`, default `infra/images/launcher/ratchet-candidate-launcher-<arch>`) and the script checks the
   uploaded copy against `launcher_sha256`, requires a native static ELF that names `/ratchet/launcher.conf`, and installs it at the
   same path, owner and mode as the C program (`/usr/local/libexec/ratchet/ratchet-candidate-ctr`, `root:root` 4755 in a 0700
   directory). `launcher.conf` itself is still written by the bench step script, as before. `90-verify-bench.sh` checks static-ness
   with the ELF program headers, not `ldd`: glibc's `ldd` exits 0 ("statically linked") for a static-pie executable, so the old
   `ldd`-must-fail check would have failed every build.
3. `ratchet-candidate-ctr.c` and `infra/tests/src/candidate-launcher.test.ts` are deleted. The latter's "compiles statically" test
   is replaced by `infra/tests/src/launcher-install.test.ts` (the install script against synthetic ELF files: digest, architecture,
   static, conf path, mode / owner as root) and the CI check on the real binary; its behavior tests live in `tests/launcher.rs`
   (table above). The `ratchet-sandbox` constants never referred to the C program (`CANDIDATE_LAUNCHER_PATH` is the sudo-launched
   shell wrapper), so nothing changed there.

Not verified: a real image build (Packer against AWS), and the shipped binary running as setuid inside a bench container on an
instance; CI executes it on a Linux runner only as root without a configuration.
