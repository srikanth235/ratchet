# Ratchet (Mac app)

The native macOS app of Ratchet, in SwiftUI. Plan: `docs/NATIVE_ARCHITECTURE.md` ("Mac app"). Look: Midnight Brass, calm
version (`design/v02.html`, `design/v02/*.png`; v0.3.1 mockups `design/v03.html`). It lives in the Ratchet repo; there is no separate git repo.

Design rules: `design/DESIGN-SYSTEM.md` (which token when). Parts and states: `design/KIT.md`. Use their tokens; never raw colors, radii, sizes or durations.

## Data

No SwiftData. Data comes from `ratchetd` through the client protocols (`Sources/RatchetKit/RatchetClient.swift`): REST-shaped
resources plus one event stream, split by domain into `OptimizationsClient` (overview, optimizations, agents, benchmarks,
templates, logs and result details), `ConnectorsClient`, `SetupClient` (repos, preflight, drafts, overrides), `SandboxClient`
and `EventsClient`. `RatchetClient` is their composition (a typealias), and a screen or a double can depend on one domain.
`ChatClient` (`Chat/`) is separate: a conversation has its own stream. `DaemonChatClient` (`/v1/chats`, one `SSEConnection` per
followed chat that resumes with `Last-Event-ID`) and `MockChatClient` (scripted drafts, create, notes, rate limit, auth expired, crash,
slow) pass one contract (`ChatClientContractTests`, the daemon side over `ChatDaemonFake`). The P6/P7 settings and the value story are
`HarnessClient` (`OptimizationSettingsClient` + `ValueStoryClient`: agents list, value model, schedule, `/v1/home`, the Overview
story), `DaemonHarnessClient` and `MockHarnessClient`; their JSON is hand-written in `Daemon/HarnessWire.swift` and `ChatWire.swift`
until the generated client holds it. View models (no views): `ChatStore`/`ChatSession` (one observable per chat; frames are batched, a
delta touches only `LiveReply`), `ComposerModel`, `ConversationModel`, `DraftCardModel`, `SteeringModel`, `AgentsPageModel`,
`OptimizationSettingsModel`, `ValueStoryModel`; the editors in `Agents/Editors.swift` are shared by the composer chips, the card rows and
the settings rows. `docs/STORIES.md` (P5b) says what each screen draws from them. Two `RatchetClient` implementations: `DaemonRatchetClient` (the real daemon,
`Sources/RatchetKit/Daemon/`) and `MockRatchetClient` (sample data, fake live events). The mock is only for test and snapshot
mode (`APP_STORE`) and `APP_DEMO=1`; every group (overview, connectors and the GitHub device flow, environment drafts,
optimizations) is real, with no sample fallback. `Tests/RatchetKitTests/ClientContractTests.swift` runs one contract against
both clients. `Store.makeStore()` (`App.swift`) builds the store on the daemon client; the daemon itself is
`DaemonController`'s job (below).

The mock is one file per domain over `MockWorld` (the sample data and what it can say about itself) and `MockSimulation` (what a
simulated minute does). `SelfTest`, `Snapshot` and tests drive it through `ClientScenario` (`AppStore.scenario`: advance time,
keychain and preflight answers), never by downcasting `store.client`.

State: `AppStore` is the root (`Sources/RatchetKit/Store/`); it owns `optimizationStore`, `connectorStore`, `sandboxStore`
and `insight` (agent logs and result details, one `@Observable` per agent log and per optimization, so a log line re-renders only
its own view), plus the overview, templates, benchmarks, repos, the time range, the shared error line (`StoreErrors`) and the
stream state. `ChatStore` is its own `@Observable`. `refresh()` loads in two waves of five requests; a part that fails is in
`sectionErrors` and the rest still loads. Each event goes through the pure `EventReducer` ((`LiveState`, event) to new state,
touched parts, notifications and effects); the store writes only the parts that changed and decides nothing else. The window
runs `store.start()` (cache, then refresh) and `store.followEvents()` as two `.task(id:)`s, so the event stream stops with the
daemon or the data source. `SnapshotCache` encodes and writes `last-snapshot.json` off the main actor, debounced; details,
logs and insights are kept for the most recent ones only.

The daemon client: `Sources/RatchetAPI/` is generated by swift-openapi-generator from `api/openapi.yaml` and committed
(`tools/generate-api.sh` regenerates it; never edit by hand). `DaemonTransport` holds the generated client and the JSON calls it
does not have, with one place that turns a failure into `RatchetClientError`. `UnixSocketTransport` carries it over the unix
socket (`HTTP1.swift` codec, `UnixSocket.swift` POSIX socket; at most eight requests open at a time), with the bearer token read
from `ratchetd.token` on every request. The routes the generated client does not hold (repo search, preflight, template
proposals, connector edits, AWS profiles, detected harnesses, draft discard, advanced settings, pull request, report, logs) are
`DaemonRatchetClient+Setup.swift`, `+Connectors.swift`, `+Optimizations.swift`, `+Insights.swift`: JSON calls through the same
transport and error middleware, one file per domain next to `+Sandbox.swift` and `+Events.swift`. `OptimizationRowsCache` shares
one table load and keeps the details of finished optimizations. `DaemonMapping` turns the daemon's view models into the app's
models. `SSEConnection` (connect, `Last-Event-ID`, backoff, cancellation) is the one event-stream connection; `DaemonEventFollower`
uses it for `/v1/events`, merges announcements that need the same refetch within 150 ms, and reports `StreamState`
(a `resync` event, or a refetch that failed, makes the store reload everything, once at a time). Secrets: the app never keeps one.
An agent API key typed in the Add connector sheet goes to `POST /v1/connectors/agents` once (a pasted GitHub token to
`POST /v1/connectors/github`) and is dropped; GitHub signs in with the device flow (`GithubSignInFlow`: the code to type is shown
on the Connectors page); the daemon files secrets in the macOS Keychain (`KeychainSecretStore`, service `ratchet`, in
`crates/ratchet-connectors`).

Naming: a *harness* is an agent CLI (Claude Code, Codex, Grok): `Harness`, `HarnessModel`, `HarnessChoice`, `HarnessCatalog`,
`DetectedHarness`. An *agent* is one running worker of an optimization. What a repo says about its benchmark is
`BenchmarkDetection`.

## The window shell (F4)

The window is the native shell; the brand lives in the content. `ContentView` is a `NavigationSplitView`: the **system sidebar**
(`Sidebar.swift`: the pages from `Page.sidebar`, then "Recent runs"; two levels, no action rows, no background or edge of its own;
a selected run wears a brass wash) and the detail column under a native toolbar. Pages: Home, Overview, Optimizations, Agents,
Benchmarks, Connectors. Command-1 to 6 follow `Page.sidebar`.

- **Toolbar** (`Toolbar.swift`): `ShellToolbar` (declared on the detail column, never on the split view) holds the connection badge
  ("Demo data", "Reconnecting…"), the sandbox status item (shape and word, popover with End Now) and New Optimization. Each page
  adds its own items (the range on Overview, the filter on Optimizations, Refresh All and Add… on Connectors, the actions on
  the open optimization) and a page-scoped `.searchable`. `SidebarCommands()` and `ToolbarCommands()` are on the scene.
- **Title and restore**: `.navigationTitle` is the page ("New Optimization" in the flow), the subtitle a count, the range or the
  open optimization's name. The window title is no longer "Ratchet", so the main window registers itself (`MainWindow`,
  `UI/WindowBehavior.swift`); never look it up by title. `@SceneStorage` restores the page and the open optimization (ids only;
  test and snapshot mode never restore).
- **Lists**: `OptimizationTable` (`Screens/Shared.swift`) is a native `Table` (selection, sorting on every column, context menu, a
  drag that carries the pull request's link, Return or double click opens). `OptimizationAction` and `OptimizationMenuItems`
  (`Screens/OptimizationActions.swift`) are the one place for Open, Run Now, Stop…, Open Pull Request, Copy Link.
- **Menus** (`FocusedActions.swift`): the table and the detail page publish the selected ids (`optimizationSelection`), the
  Optimization menu, Export Report… and Add Connector… (File) and Find… (Edit) act on them. Stop never acts at once: it sets
  `router.pendingStop` and the window shows one confirmation ("Stop Checkout p95?", "Wins found so far are kept."). Reversible
  actions register Undo (Make Default, removing an AWS profile). "Run Now" starts an optimization that has not started
  (`OptimizationsClient.runOptimization`, the daemon's `/start`).
- **Settings**: four tabs, each one grouped `Form`, all 520 wide: General (menu bar, "Default for new optimizations"),
  Notifications, This Mac (background service with Stop and Demo mode behind a confirmation, login item, command-line tool) and
  Advanced. Templates, Connectors and agents are not in Settings.
- **Liquid Glass**: sheets, popovers, bars and the menu bar window have no custom background. Floating surfaces (`KitComposer`,
  `KitSteeringField`) are `.glassEffect()` inside a `KitGlassContainer`; P5b fills the containers and anchors them with
  `.safeAreaInset(edge: .bottom)`. Custom chrome calls `.dimsWhenInactive()` (`appearsActive`).
- **Daemon down**: with data on screen, `DaemonBanner` sits above every page and `\.daemonActionsEnabled` is false, which
  disables New Optimization, Stop, Run Now, Open Pull Request, Add Connector… and End Now. Without data the full-window
  `DaemonStatusView` stays. Empty, loading and failed-connector states are in `States.swift` and `ConnectorRow`; a broken
  status always has its fix beside it (Sign in, Add key, Re-detect).
- **Layout**: one content width (`Layout.contentWidth`) in `KitPage`; the page margin is `Space.pageX`, passed to `.gridArea(_,
  inset:)`; side columns use `ViewThatFits`; nested radii use `ConcentricRectangle`; the ⋯ of a row is `KitMoreMenu` (28 pt hit area).

## The chat screens (P5b)

`ChatHub` (`ChatHub.swift`, in the environment next to `AppStore`) owns what P5a built: `ChatStore`, `ValueStoryModel`, `AgentsPageModel`,
`ComposerModel`, and hands out `ConversationModel`, `DraftCardModel`, `SteeringModel` and `OptimizationSettingsModel` by id. Sample clients in
test, snapshot and `APP_DEMO` mode, the daemon's otherwise. Screens (`Screens/Home`, `Chat`, `Run`, `OptimizationDetail`, `AgentsPage`, `OverviewPage`):

- **Home** (`HomePage`): value header (`ValueStory`, the same words as the Overview), glass `KitComposer` with five `PopoverChip`s (repo, cloud,
  agents, limits, schedule), Return or Command-Return sends, suggestions, the first-use notice. Send opens the **creation conversation**
  (`router.creationChatID`; `CreationView`, `DraftCardView`) in Home's place. It replaces the old wizard screens (ADR 0001; the logic stays in
  RatchetKit). "Use Template…" starts the same conversation with the template chosen (`ChatHub.startFromTemplate`). Nothing waits on a person:
  there is no Approve step, and an optimization that was created and not started reads "Not started".
- **Optimization page** has two tabs (`router.detailTab`): Run (`RunHeader`: status word, Run Now, Stop…, Pause Schedule or Pause Agent, Open PR,
  a ⋯ menu with Archive…; the log in three views in `RunLogSection`; the glass `SteeringBar`) and Settings (`OptimizationSettingsView`: rows with
  tags, Edit popovers, Saved; Archive…). Pause Schedule clears the schedule and remembers it for Resume (this session only).
- **Agents** (`AgentsPage`), **Overview** (`OverviewPage`, `ValueChart` with the dashed pending step and a text equivalent), the Connectors
  **Yours | Discover** row (not on Agents), the menu bar's "Keeping your Mac awake" line (`AppStore.power`).
- Popovers (`Chat/Popovers.swift`) are shared by the chips, the card rows and the settings rows. Snapshot scenes: `home*`, `conversation-*`,
  `run-*`, `optimization-settings*`, `agents-signin`, `overview-nowins`, `connectors-discover`, `menubar-awake`; the self-test drives a simulated
  chat to a created optimization (`SelfTestChat.swift`).

## The bundled daemon

`./build.sh` also builds the Rust helpers (`tools/build-helpers.sh`, host arch; `--universal` for arm64 + x86_64 joined with `lipo`) and puts
them in the bundle. Needs a Rust toolchain; `RATCHET_SKIP_DAEMON=1` skips it for a UI-only build.

```text
Ratchet.app/Contents/
  MacOS/Ratchet                                  the app
  Helpers/ratchetd, Helpers/ratchet              the daemon and the CLI (signed with identifiers com.ratchet.*)
  Library/LaunchAgents/com.ratchet.ratchetd.plist        BundleProgram Contents/Helpers/ratchetd, serve --mode real --log-to-support-dir
  Library/LaunchAgents/com.ratchet.ratchetd.demo.plist   the same with --mode sim --ledger :memory: (demo mode)
```

The plists come from `ratchetd launchagent print --bundle-program ... [--demo]`. `DaemonController` (app target) registers one of them with
`SMAppService.agent(plistName:)` on first launch; the rules (register, wait for the socket, approval in Login Items, restart, stop, switch
to demo) are `DaemonLifecycle` in RatchetKit, a pure state machine with tests. While the socket is silent the window shows
`DaemonStatusView` ("Starting Ratchet…", or the Login Items prompt, or a failure with Try again). Settings, This Mac, has Restart / Stop… / Demo
mode / Open Log (Stop and Demo mode ask first). A daemon you start yourself is used as is: set `RATCHET_HOME=<dir>` (or `RATCHET_SOCKET`) and the app only watches
that socket and registers nothing. A build with no `ratchetd` inside (`RATCHET_SKIP_DAEMON=1`, or the Rust build failed) and no `RATCHET_HOME`
is `Management.unbundled`: `DaemonStatusView` says "This build has no background service" at once (not after 40 s of "Starting…"), and
`build.sh` ends with a loud WARNING box. A new build can meet the previous build's daemon, because the LaunchAgent outlives the app: once per
launch the app compares `GET /v1/status` `version` with `Contents/Helpers/ratchetd --version` (`DaemonVersionCheck`, RatchetKit) and restarts
the agent on a mismatch. `build.sh --open` quits the app and runs `launchctl bootout gui/$UID/com.ratchet.ratchetd` (and `.demo`) before it
replaces the bundle; the app registers the agent again, and if the agent is enabled yet nothing answers after 4 s it unregisters and registers
once more. On `didBecomeActive` the app rechecks the daemon, the login item and the notification permission, and Settings polls every 2 s
while one of them is missing (System Settings changes do not always notify the app).

The `ratchet` CLI: Settings > Command line links it into `~/.local/bin` (the user's folder; no password) and says how to add that folder to
`PATH` when a login shell does not have it. "Install for all users…" links `/usr/local/bin` through the system's administrator prompt, only on
request. `CommandLineLinkState` (RatchetKit) names what is at a link: missing, linked, **broken** (target gone), another copy of the app, or a
file that is not ours (never replaced). Settings shows each state and "Repair" for a broken link.

Dev loop: `cargo run -p ratchetd -- serve --mode sim` in one terminal, `RATCHET_HOME=<its dir> ~/Applications/Ratchet.app/Contents/MacOS/Ratchet` in
another (the dir is printed in the log; on macOS `~/Library/Application Support/Ratchet` is both the default and what the bundled agent uses, so
stop the agent first: Settings, Stop). CI runs the same thing with `tools/smoke-daemon.sh`.

## Notifications

`AppNotifier` (UNUserNotificationCenter). Permission is never asked at launch: the Overview shows a calm card once an optimization exists
(`NotificationPrompt`), and Settings has a button. Posted only while the app is in the background. Categories (`NotificationCategory`, one
switch each in Settings): win ready to merge, environment drafted, budget limit, run finished or failed, connector expired. A click opens the
screen (`NotificationDestination`: the optimization, Connectors, or Home with the composer). `NotificationRouting` (RatchetKit) is the pure
decision function over two store states; the store calls it after each event and never on the first load.

## URL scheme and `ratchet open`

`Info.plist.in` registers `ratchet://`. `ContentView` handles it with `.onOpenURL`, through `AppLink` (RatchetKit): `ratchet://open/<page or
optimization id>`, `ratchet://optimization/<id>`, `ratchet://connectors|new|overview`, `ratchet://<page>`. Places a notification click can open
go through `NotificationDestination(token:)`, the same parser, and through `AppNotifier.open`, so a link and a click cannot disagree. A click or
link that arrives before the window has set `onOpen` (a cold launch) waits in `PendingDestination` and is delivered when the handler is set.
`ratchet open <page|id>` (the CLI, no daemon needed) builds the link and hands it to `/usr/bin/open`; `--print` only prints it.

## Debug bridge (debug builds only)

`./build.sh --debug` compiles `DebugBridge.swift`; a release build has no channel. The running app polls `<home>/bridge/inbox/<id>.cmd`
(`<home>` = `$RATCHET_HOME`, else `~/Library/Application Support/Ratchet`) and answers in `<home>/bridge/outbox/<id>.json` (`BridgeReply`,
protocol and tests in RatchetKit). `tools/ratchetctl.sh <command>` is the client (prints the JSON; exit 0 ok, 1 refused, 2 no answer):

| Command | Does |
|---|---|
| `status` | JSON `status`: `page`, `selectedOptimization`, `wizardOpen`, `daemonPhase`, `daemonDetail`, `notificationAuth`, `appearance`, counts, `lastError`, `testMode`, `pid`; also `bridge/status.json` |
| `open:<page\|id>` | A page by name, or an optimization id (`AppLink` rules) |
| `appearance:light\|dark` | Switches the app's appearance |
| `snapshot:<scene>` | A window PNG in `bridge/snapshots/<scene>-<appearance>.png` (any `SnapScene`, e.g. `menubar`, `daemon-failed`; test mode) |
| `selftest` | The self-test inside the running app (`checks`, `failures`, `lines`; test mode, once per launch, so run it first) |

`tools/bridge-test.sh` starts a debug build in test mode (`APP_STORE=…`, a private `RATCHET_HOME`) and drives all of it; CI runs it
("Debug bridge" step). Typical agent loop: `RATCHET_HOME=/tmp/r APP_STORE=/tmp/r.store …/Ratchet &`, then `RATCHET_HOME=/tmp/r tools/ratchetctl.sh open:connectors`.

## Errors and launch at login

`AppStore.lastError` is shown in `ErrorBanner` (`DesignKit/Banner.swift`) above the page, in `ContentView`: dismissible, and cleared when the
next action starts (`beginAction()` in every store action) or on the close button (`dismissError()`). A failed Stop, pull request or End
sandbox says what it was doing ("Couldn't stop the optimization. …"). A failed load clears on the next good load; a failed action is not
wiped by a background refresh. Snapshot scene: `error-banner`.

Settings > Startup has "Launch at login" (`LoginItem`, `SMAppService.mainApp`). A login launch (the open-application event carries
'lgit', see `LaunchContext`) shows only the menu bar item: the window is hidden, not closed, so data keeps loading and notifications keep
coming; the menu bar item, a notification click or the Dock icon brings it back. It needs the menu bar item, so turning it on turns that on.
Test and snapshot mode never register anything. Snapshot: `settings-login-approval`.

## Rules

- Spacing comes from `Space` (`UI/Grid.swift`), on a 4 pt grid; control sizes and radii are `Dim`, shared widths `Layout` (`DesignKit/Tokens.swift`), all on the grid.
- Colors only through `Ink` (light and dark values), fonts only through `.kitType(...)`, icons through `KitIcon`.
- Parts are real controls (`Button` with a `ButtonStyle`), never a shape with a tap gesture. Each takes `forcedPartState` and is shown in every state in `KitGallery`.
- `.tint(Ink.brass)` is set at each scene root; motion only through `Motion` (nil under Reduce Motion).
- Window chrome (title bar, toolbar, sidebar, menus, sheets, popovers) stays system: no custom background behind it. Every action has a menu item and a shortcut: Command-N new optimization, Command-1 to 9 for the pages in `Page.sidebar` order.
- Pure app logic (menu bar `timeFraction`/`runNote`/`sandboxLine`, the CLI link states, route rules, links, the debug bridge protocol) lives in RatchetKit with tests, not in views.
- Money, percents and durations go through `Money`, `Percent`, `Elapsed` in the Kit, so the tests cover them.
- Main-actor default isolation in the app target; the Kit target is nonisolated, its types are `Sendable` structs, `MockRatchetClient` is an actor and `DaemonRatchetClient` a `Sendable` class. The stores are `@MainActor @Observable` classes.
- Decisions: `docs/adr/` (0001: the composer replaces the wizard's screens, not its logic).
