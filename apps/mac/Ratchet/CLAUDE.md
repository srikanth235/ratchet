# Ratchet (Mac app)

The native macOS app of Ratchet, in SwiftUI. Plan: `docs/NATIVE_ARCHITECTURE.md` ("Mac app"). Look: Midnight Brass, calm
version (`design/v02.html`, `design/v02/*.png`). It lives in the Ratchet repo; there is no separate git repo.

## Data

No SwiftData. Data comes from `ratchetd` through the client protocols (`Sources/RatchetKit/RatchetClient.swift`): REST-shaped
resources plus one event stream, split by domain into `OptimizationsClient` (overview, optimizations, agents, benchmarks,
templates, logs and result details), `ConnectorsClient`, `SetupClient` (repos, preflight, drafts, overrides), `SandboxClient`
and `EventsClient`. `RatchetClient` is their composition (a typealias), and a screen or a double can depend on one domain.
`ChatClient` (`Chat/`) is separate: a conversation has its own stream; it has a protocol, models and `MockChatClient`, and no
daemon implementation or UI yet (P5). Two `RatchetClient` implementations: `DaemonRatchetClient` (the real daemon,
`Sources/RatchetKit/Daemon/`) and `MockRatchetClient` (sample data, fake live events). The mock is only for test and snapshot
mode (`APP_STORE`) and `APP_DEMO=1`; every group (overview, connectors and the GitHub device flow, environment drafts,
optimizations) is real, with no sample fallback. `Tests/RatchetKitTests/ClientContractTests.swift` runs one contract against
both clients. `Store.makeStore()` (`App.swift`) builds the store on the daemon client; the daemon itself is
`DaemonController`'s job (below).

The mock is one file per domain over `MockWorld` (the sample data and what it can say about itself) and `MockSimulation` (what a
simulated minute does). `SelfTest`, `Snapshot` and tests drive it through `ClientScenario` (`AppStore.scenario`: advance time,
keychain and preflight answers), never by downcasting `store.client`.

State: `AppStore` is the root (`Sources/RatchetKit/Store/`); it owns `optimizationStore`, `connectorStore`, `sandboxStore`
and `insight` (agent logs and result details, one `@Observable` per agent log and per optimization, so a log line re-renders only
its own view), plus the overview, templates, benchmarks, repos, the time range, the shared error line (`StoreErrors`) and the
stream state. `ChatStore` is its own `@Observable`. `refresh()` loads in two waves of five requests; a part that fails is in
`sectionErrors` and the rest still loads. Each event goes through the pure `EventReducer` ((`LiveState`, event) to new state,
touched parts, notifications and effects); the store writes only the parts that changed and decides nothing else. The window
runs `store.start()` (cache, then refresh) and `store.followEvents()` as two `.task(id:)`s, so the event stream stops with the
daemon or the data source. `SnapshotCache` encodes and writes `last-snapshot.json` off the main actor, debounced; details,
logs and insights are kept for the most recent ones only.

The daemon client: `Sources/RatchetAPI/` is generated by swift-openapi-generator from `api/openapi.yaml` and committed
(`tools/generate-api.sh` regenerates it; never edit by hand). `DaemonTransport` holds the generated client and the JSON calls it
does not have, with one place that turns a failure into `RatchetClientError`. `UnixSocketTransport` carries it over the unix
socket (`HTTP1.swift` codec, `UnixSocket.swift` POSIX socket; at most eight requests open at a time), with the bearer token read
from `ratchetd.token` on every request. The routes the generated client does not hold (repo search, preflight, template
proposals, connector edits, AWS profiles, detected harnesses, draft discard, advanced settings, pull request, report, logs) are
`DaemonRatchetClient+Setup.swift`, `+Connectors.swift`, `+Optimizations.swift`, `+Insights.swift`: JSON calls through the same
transport and error middleware, one file per domain next to `+Sandbox.swift` and `+Events.swift`. `OptimizationRowsCache` shares
one table load and keeps the details of finished optimizations. `DaemonMapping` turns the daemon's view models into the app's
models. `SSEConnection` (connect, `Last-Event-ID`, backoff, cancellation) is the one event-stream connection; `DaemonEventFollower`
uses it for `/v1/events`, merges announcements that need the same refetch within 150 ms, and reports `StreamState`
(a `resync` event, or a refetch that failed, makes the store reload everything, once at a time). Secrets: the app never keeps one.
An agent API key typed in the Add connector sheet goes to `POST /v1/connectors/agents` once (a pasted GitHub token to
`POST /v1/connectors/github`) and is dropped; GitHub signs in with the device flow (`GithubSignInFlow`: the code to type is shown
on the Connectors page); the daemon files secrets in the macOS Keychain (`KeychainSecretStore`, service `ratchet`, in
`crates/ratchet-connectors`).

Naming: a *harness* is an agent CLI (Claude Code, Codex, Grok): `Harness`, `HarnessModel`, `HarnessChoice`, `HarnessCatalog`,
`DetectedHarness`. An *agent* is one running worker of an optimization. What a repo says about its benchmark is
`BenchmarkDetection`.

## The bundled daemon

`./build.sh` also builds the Rust helpers (`tools/build-helpers.sh`, host arch; `--universal` for arm64 + x86_64 joined with `lipo`) and puts
them in the bundle. Needs a Rust toolchain; `RATCHET_SKIP_DAEMON=1` skips it for a UI-only build.

```text
Ratchet.app/Contents/
  MacOS/Ratchet                                  the app
  Helpers/ratchetd, Helpers/ratchet              the daemon and the CLI (signed with identifiers com.ratchet.*)
  Library/LaunchAgents/com.ratchet.ratchetd.plist        BundleProgram Contents/Helpers/ratchetd, serve --mode real --log-to-support-dir
  Library/LaunchAgents/com.ratchet.ratchetd.demo.plist   the same with --mode sim --ledger :memory: (demo mode)
```

The plists come from `ratchetd launchagent print --bundle-program ... [--demo]`. `DaemonController` (app target) registers one of them with
`SMAppService.agent(plistName:)` on first launch; the rules (register, wait for the socket, approval in Login Items, restart, stop, switch
to demo) are `DaemonLifecycle` in RatchetKit, a pure state machine with tests. While the socket is silent the window shows
`DaemonStatusView` ("Starting Ratchet…", or the Login Items prompt, or a failure with Try again). Settings has Restart / Stop / Demo mode /
Open log and notifications. A daemon you start yourself is used as is: set `RATCHET_HOME=<dir>` (or `RATCHET_SOCKET`) and the app only watches
that socket and registers nothing. The `ratchet` CLI is linked into `/usr/local/bin` only when the user clicks "Install command line tool".

Dev loop: `cargo run -p ratchetd -- serve --mode sim` in one terminal, `RATCHET_HOME=<its dir> ~/Applications/Ratchet.app/Contents/MacOS/Ratchet` in
another (the dir is printed in the log; on macOS `~/Library/Application Support/Ratchet` is both the default and what the bundled agent uses, so
stop the agent first: Settings, Stop). CI runs the same thing with `tools/smoke-daemon.sh`.

## Notifications

`AppNotifier` (UNUserNotificationCenter). Permission is never asked at launch: the Overview shows a calm card once an optimization exists
(`NotificationPrompt`), and Settings has a button. Posted only while the app is in the background. Categories (`NotificationCategory`, one
switch each in Settings): win ready to merge, environment drafted, budget limit, run finished or failed, connector expired. A click opens the
screen (`NotificationDestination`: the optimization, Connectors, or the New optimization flow). `NotificationRouting` (RatchetKit) is the pure
decision function over two store states; the store calls it after each event and never on the first load.

## Errors and launch at login

`AppStore.lastError` is shown in `ErrorBanner` (`DesignKit/Banner.swift`) above the page, in `ContentView`: dismissible, and cleared when the
next action starts (`beginAction()` in every store action) or on the close button (`dismissError()`). A failed Stop, pull request or End
sandbox says what it was doing ("Couldn't stop the optimization. …"). A failed load clears on the next good load; a failed action is not
wiped by a background refresh. Snapshot scene: `error-banner`.

Settings > Startup has "Launch at login" (`LoginItem`, `SMAppService.mainApp`). A login launch (the open-application event carries
'lgit', see `LaunchContext`) shows only the menu bar item: the window is hidden, not closed, so data keeps loading and notifications keep
coming; the menu bar item, a notification click or the Dock icon brings it back. It needs the menu bar item, so turning it on turns that on.
Test and snapshot mode never register anything. Snapshot: `settings-login-approval`.

## Layout

- `Sources/RatchetAPI/` generated OpenAPI types and client (see Data). `Sources/RatchetKit/` models (`Models/`, `Setup/`, `Insights/`), formatting, client protocols, mock, `Daemon/`, `Chat/`, `Store/`, `NewOptimizationFlow`, `AddConnectorForm`. No SwiftUI. Tests in `Tests/RatchetKitTests/`.
- `Sources/Ratchet/` the app: `App.swift` (scenes, commands, `Store`), `ContentView.swift`, `Sidebar.swift`, `Pages.swift` (the `Page` enum: title, icon, availability, shortcut and destination of each page), `Router.swift`, `MenuBarView.swift`, `SettingsView.swift`, `Snapshot.swift`, `SelfTest.swift`, `DaemonController.swift`, `DaemonStatusView.swift`, `AppNotifier.swift`, `NotificationPrompt.swift`, `CommandLineTool.swift`.
- `Sources/Ratchet/Screens/` one file per screen, a folder when a screen has several views: Overview, Optimizations, `OptimizationDetail/`, New optimization steps, Benchmarks, `Connectors/` (page, row, edit form, device-flow card, Add sheet, `ConnectorsPageState`).
- `Sources/Ratchet/DesignKit/` the design kit: `Tokens.swift` (Palette, Ink, Dim, Motion), `Type.swift`, `Icons.swift`, `Buttons.swift`, `Rows.swift`, `Choice.swift`, `Page.swift`.
- `Sources/Ratchet/UI/` `Grid.swift` (the 4 pt scale, layout probes), `WindowBehavior.swift`.

## Build and check

- Build and install: `./build.sh` (`--open` restarts the app). Prints the compiler errors with context on failure.
- Unit tests: `swift test --scratch-path ~/Library/Developer/Ratchet/test-build`.
- Self-test: `tools/selftest.sh` (exit 0 when every check passes, on the sample client). Add a check for every story with logic. `tools/smoke-daemon.sh` starts the bundled `ratchetd serve --mode sim` on a temp socket and runs `Ratchet --selftest-live` against it (the real client path); CI runs both.
- Snapshots: `tools/snap.sh` writes `/tmp/Ratchet-shots/<scene>-light.png` and `-dark.png` for the four pages, the optimization detail (live, finished, no win), the four New optimization steps, and `settings-<tab>-*.png`, and the states `daemon-starting`, `daemon-approval`, `notification-prompt`, `connector-signin`, and the setup states `new-repo-found`, `new-repo-invalid`, `new-repo-template`, `new-local-folder`, `new-local-noremote`, `new-missing`, `connectors-add-github`, `connectors-add-aws`, `connectors-add-agent`, `connectors-edit`, `connectors-rename`, `connectors-check`, `connectors-keychain`, `template-pr`, `settings-advanced`. `APP_SNAPSHOT_PAGES=overview,new-budget tools/snap.sh` limits the scenes.
- Grid: `tools/grid-lint.sh`, then `swift tools/check-layout.swift /tmp/Ratchet-shots/*-layout.json`.
- API client: `tools/generate-api.sh` after `api/openapi.yaml` changes (needs network once for the generator). Live check against a real daemon: `RATCHET_LIVE_HOME=<dir of a running ratchetd> swift test --filter LiveDaemon`.
- Test mode: `APP_STORE=<file in /tmp>` means a fixed clock, no live ticks and no saved snapshot.
- CI: `.github/workflows/native.yml`, job `mac-app` (macOS 26).

## Rules

- Spacing comes from `Space` (`UI/Grid.swift`), on a 4 pt grid; the design's own odd sizes (3, 7, 15 pt) live in `DesignKit/Tokens.swift` as `Dim`.
- Colors only through `Ink` (light and dark values), fonts only through `.kitType(...)`, icons through `KitIcon`.
- Parts are real controls (`Button` with a `ButtonStyle`), never a shape with a tap gesture.
- Window chrome (title bar, toolbar, menus, sheets, popovers) stays system. Every action has a menu item and a shortcut: Command-N new optimization, Command-1 to 9 for the pages in `Page.sidebar` order.
- Money, percents and durations go through `Money`, `Percent`, `Elapsed` in the Kit, so the tests cover them.
- Main-actor default isolation in the app target; the Kit target is nonisolated, its types are `Sendable` structs, `MockRatchetClient` is an actor and `DaemonRatchetClient` a `Sendable` class. The stores are `@MainActor @Observable` classes.
- Decisions: `docs/adr/` (0001: the composer replaces the wizard's screens, not its logic).
